## 1. 设计目标

产品能力与优先级以需求第4节为准。本文件规定各模块如何协作；本地原生RTT必需，远程变量与网页RTT手动互斥使用，TCP远程串口暂缓。

维护目标是让公共调试工具只有一个源码来源，让工程文件适配只有一个入口，让软件使用者不需要复制并自行修改 Python 脚本。Release 负责分发版本化工具；配置含义和工具调用协议负责稳定上下游关系。


采集工作进程与 CLI 是不同职责：前者负责持续变量/RTT采集，后者为 VS Code/EIDE 提供稳定的后台工具调用入口。二者共享配置与会话规则，均不在界面线程执行硬件操作。

变量由客户端经USB或Remote Server连接探针采集，并在本地解析ELF。本地原生RTT使用客户端SDK；远程RTT沿用独立网页及Logger，与客户端远程变量采集手动切换。当前架构不建设TCP串口适配器。

### 2.1 统一入口与既有工具的边界

“一站式”先统一操作入口和项目上下文，不要求所有功能立刻改成同一种界面或同一个进程。

| 用户操作 | 承担功能的一方 | 小助手职责 |
| --- | --- | --- |
| 编辑、构建、源码调试 | VS Code/EIDE与原调试工具 | 读取/维护项目配置，提供兼容接入 |
| 变量列表与曲线 | 小助手及采集工作进程 | 解析项目ELF，经本地/远程J-Link采集 |
| 使用已有网页RTT | LAN-Debug-Server网页及服务端Logger | 调用系统默认浏览器打开原网页 |
| 使用本地原生RTT面板 | 客户端SDK采集 | 首版必需，按VIS-07及AC-04验证 |
| 使用远程RTT | 现有网页及服务端Logger | 与远程变量采集手动互斥；不做跨源时序对齐 |
| 本地串口收发 | 小助手串口工具 | 独立于项目与服务端运行 |

打开网页无需捆绑Chrome，不等于内嵌WebView，也不等于小助手通过HTTP拉取RTT数据。后三者有不同的开发和兼容成本，不能混写成一个“接入RTT”需求。网页与原生采集若指向同一探针，仍需手动释放占用；多一个入口不会消除占用问题。

演进顺序建议：复用现有网页入口 → 在确有统一面板需求时定义兼容的数据/控制接口 → 新旧调用方验证后再协同淘汰旧实现。接口改造前不复制网页业务逻辑，不新增常驻代理，不要求旧服务升级才能使用已有功能。

## 3. 模块划分

| 模块 | 职责 | 输入/输出 | 主要约束 |
| --- | --- | --- | --- |
| GUI | 调试主页、配置页、工具窗口、状态呈现 | 用户操作/应用状态 | 不直接持有 SDK 句柄或编辑工程文件 |
| 应用协调层 | 编排打开工程、应用配置、切换连接和升级 | 用例命令/结果与事件 | 不复制底层配置和驱动规则 |
| 工程识别 | 定位根目录、识别系列/版本/构建目标 | 路径/工程快照 | 多匹配时显式选择 |
| 模板适配 | 读取及映射 EIDE、VS Code、CubeMX 约定 | 原文件/标准工程模型 | 分版本、分系列验证，不依赖整库字符串替换 |
| 配置管理 | 生成变更计划、并发检查、写入与恢复 | 编辑模型/变更集合 | 保留未知字段和用户内容 |
| ELF 服务 | 建立变量/类型索引，形成读取计划 | ELF/地址与类型描述 | 与目标运行状态分离，校验 ELF变化 |
| 会话管理 | 开始/停止采集、切换连接、错误重试 | 端点/会话状态 | 停止时释放探针；源码调试互斥，手动切换 |
| 采集工作进程 | 变量读取、RTT单消费者、数据输出 | 读取计划/采集事件 | SDK 操作隔离，异常不拖垮 GUI |
| CLI/工具入口 | 给 VS Code/EIDE 调用已安装版本 | 参数/输出、退出码 | GUI不运行也可工作 |
| 串口服务 | 原始收发、控制参数、独立生命周期 | 端口/字节与统计 | 与工程和 J-Link 解耦 |
| Release 管理 | 离线导入、在线查询、安装和选版 | 发布包/缓存元数据 | 版本目录不可原地替换，离线可运行 |
| 记录服务 | 上位机保存串口双向字节、方向、连续序号和分段；时间可选 | 数据事件/记录文件 | SER-04为P0，不要求固件改造；统一记录回放为P1 |

核心逻辑可以同仓库内分模块维护，不要求每个模块单独建仓库、服务或包。

## 5. 技术路线与验证边界

产品采用C#、WPF和.NET 10 LTS，首批Windows 11 x64验收，自包含单EXE。WPF使用适度MVVM、变量表/曲线/可折叠RTT区域，不先建设插件平台或复杂停靠系统。核心模型与WPF分离，当前不承诺跨平台。

ELF/DWARF4使用LibObjectFile 2.3.1受限标量索引。真实G4产物采用DWARF5，内置库不支持，故由已有ARM readelf只读输出提供兼容解析；缺工具提示配置路径或使用-gdwarf-4，不修改工程编译参数。YamlDotNet 18.1.0读取EIDE并配合局部字段写入，JSONC按值位置修改；System.IO.Ports 10.0.12提供串口。初版曲线用有界WPF折线，不引入ScottPlot；未宣称30分钟性能通过。SDK由独立C#工作进程动态绑定，GUI不装载DLL；异常与阻塞隔离规则沿用第8节。

Python/Qt产品路线结束，历史原型与依赖通过Git归档，样本和结论保留，标准库Python Harness继续使用。若真实ELF证明纯C#候选不能满足范围，先记录具体失败，再评估封装既有解析器的体积/维护代价；不预建两套后端或自研完整DWARF。

工具升级通过稳定CLI定位缓存中的精确版本，让兼容Debug_LAN修复独立于GUI发布。配置写入只实现已支持工程的一键接入，局部修改.vscode并保留原任务，不以通用编辑器为前置条件；EIDE写入样本已验证，真实上传仍须验收。C#实现不自动继承Python配置往返或有序记录的测试结果。

用户交付为自包含单EXE；启动后自动准备内部GUI、CLI及工作进程，保持进程职责隔离。

### 6.2 配置权威来源

- 原有工程文件仍是相应能力的真实输入，小助手读取后形成标准化模型。
- 本地/远程观察配置可以同时保存，但当前观察模式不直接改变 EIDE/VS Code 方案。
- 共用芯片、ELF、端口等字段的多个消费者由配置管理一次生成变更计划；不创建第二份 GUI 专用芯片值覆盖真实文件。
- 有冲突时呈现来源和候选值，在保存前解决；芯片名称的工具写法通过已验证映射转换。
- MCU更换涉及固件工程生成和编译，首版 GUI只检查，不擅自同步 .ioc/芯片宏。

### 6.3 修改权限

初次接入只修改所选目标和产品管理的条目。JSONC/YAML等文件需保留未知内容及有效注释。不得重写整个工程为内置样板。

EIDE 3.27.2 Custom CLI结构及命令消费已核对，四模板样本的局部写入、读回、幂等和移除恢复已验证；真实EIDE上传和设备结果另行验收。

## 7. UI 与操作流程

### 7.1 主要页面

1. 工程：包含工程概览和远程配置两个子页；共享连接配置由右上角独立窗口维护；维护目标/ELF、共享连接、预览并应用接入。
2. 查看变量：读取工程内已保存参数，显示数值与曲线、RTT及采集状态；缺项引导到对应设置页。
3. 串口助手：与工程及J-Link会话独立，无工程时仍可使用。
4. 设置与诊断：维护本机DLL/readelf路径、工具版本与入口绑定、环境诊断和日志。

界面使用功能性状态而不是内部实现术语。配置有效、探针连接与有新数据分别显示，避免把“进程启动”显示成“数据正常”。

### 7.2 打开工程

选择路径 → 建立快照 → 选择模板/目标 → 验证配置和 ELF → 加载布局。读取阶段不接探针、不改文件、不运行构建/烧录。

### 7.3 应用远程接入

填写参数和接入选项 → 生成文件级变更计划 → 展示影响 → 应用并校验 → 报告完成/回滚。用户点击“应用”作为日常操作，无需每个字段重复确认。

接入计划按REM-02、REM-05、REM-07处理可选烧录、条目归属和旧入口兼容；同项目复用按PRJ-07。具体迁移及兼容检查见详细设计第6节。

### 7.4 观察连接切换

停止当前采集 → 排空/标记当前数据边界 → 释放当前连接 → 验证新端点 → 连接新目标 → 重新确认读取计划 → 恢复采集。布局不重建，时间线标记新的连接/会话代次。

### 7.5 后续界面打磨边界

已实施紧凑样式、五项导航、工程子页和局部状态绑定，现行职责见7.1、7.6、7.7。继续打磨最小窗口、不同DPI、键盘路径、就地错误和数据解释，按实际问题逐项回归。曲线已提供名称、窗口数值范围与分道独立缩放；横轴仍为显示点顺序，真实时间轴和手动缩放手势另行讨论。

MCU Viewer主页面和添加弹窗共用VariablePicker及同一变量集合：主页面仅显示已添加变量及移除操作，弹窗仅显示搜索和添加操作。关闭弹窗后解除集合订阅；采集中禁止修改，保存沿用工程watch.json。新配置默认200 Hz，已保存频率优先。LAN_Debug的r1唯一采集、统一日志与API也只作为后续讨论方向，不能覆盖第2节当前SDK直连和网页手动互斥的实现。

### 7.6 紧凑专业界面（R-06、R-07）

当前职责以R-22迁移方案为准：工程、MCU Viewer、RTT监视、串口助手、设置与诊断五个入口；工程连接配置共享，变量采样和RTT日志独立。颜色和控件样式继续复用WPF资源，全量MVVM与曲线时间轴语义仍暂缓。

### 7.7 观察协调与渐进绑定（R-11）

ObservationPreparation在Core中读取已保存watch与远程JSON，并通过传入的ELF索引函数产生PreparedObservation：完整连接请求、变量索引、工程/目标身份及ELF时间；准备不加载SDK或创建工作进程。失败带配置区域，由窗口映射补全入口。窗口开始前重新准备并核对工程/目标；采集参数不再借用远程编辑框或串口输入。准备只更新查看状态和变量投影，不覆盖远程连接编辑草稿。

ObservationCoordinator拥有唯一ObservationSession，串行启停和计划更新；停止等待正在进行的启动/更新，释放失败保留原会话并禁止新建，重试先完成释放。窗口只转发操作、维护展示数据及WPF关闭入口；退出等待准备、工程读取、ELF索引与配置写入，随后独立关闭串口、停止观察。串口由SerialController协调会话及PeriodicSender，保持与工程/J-Link独立；周期发送沿用逐次读取当前发送内容的行为。

ObservationViewModel绑定查看页摘要、缺项、按钮、暂停、列表、RTT和曲线快照；RemoteViewModel维护编辑输入和预览，输入/目标/工具选版变化使旧预览失效，应用/恢复期间锁定编辑与工程切换；SerialViewModel绑定连接灯、文字、参数与周期按钮。保留现有View事件，不引入通用消息总线、状态机框架或新的运行包。设置保存读取本机工具路径、窗口参数及无需解析硬件参数的显示编码，串口成功打开后独立保存已校验的串口偏好。

ObservationPlot以StreamGeometry渲染独立快照，按像素桶保留极值，缓存同一快照/尺寸的几何；窗口保持10Hz刷新，每轮观察/串口消费各限制256项或8ms，隐藏页继续消费但跳过昂贵展示。曲线仍是最近2000个数值点、最多16条，横轴仍按点序号；不把抽稀后的显示当作完整原始记录，不据短时渲染检查声明30分钟性能或硬件通过。

## 8. J-Link 会话与外部工具协作

首版状态为未连接、连接中、采集中、停止中和故障。会话管理器负责本产品采集进程，停止采集同时关闭SDK连接并释放探针；“暂停显示”仍保持采集。

同一采集进程持有一个 SDK连接，串行调度读变量与RTT操作。RTT只被读取一次，数据再分发。不同探针可以后续建立不同进程，首版先验证单探针。

源码调试保留现有 SEGGER GDB Server 和 VS Code Cortex-Debug链路；稳定CLI负责选择版本、启动、输出就绪状态和跟踪自己启动的进程，不实现GDB Server或全局探针租约。

首版参考Viewer的手动切换流程：

1. 用户点击停止采集，关闭SDK连接。
2. 用户在VS Code/EIDE中烧录或源码调试。
3. 调试结束后，用户点击开始采集，复用观察列表和布局。
4. 若另一工具仍占用探针，显示连接错误，用户停止该工具后重试。本产品故障后的重试必须先完成旧连接清理，旧句柄未关闭或旧工作进程未退出时不得建立新连接。

首版不实现后台协调器、租约、外部调试器自动发现或自动恢复采集。未来确有需要再添加自动交接，不把这些作为当前交付条件。

网页RTT如占用同一探针，由用户在服务端停止后再连接客户端。首版提供操作说明和错误反馈，不依赖新增服务端交接协议。

## 9. 数据处理架构

### 9.1 变量

ELF服务解析固定地址变量，形成名称、地址、长度和类型的读取计划。采集器仅接收已验证计划，按实际地址读字节，解码层转为展示值。

首版按ELF中选定变量的地址和长度逐项读取，失败显示无效值。暂不合并相邻地址，也不要求完整safeMemoryRegion数据库；未来优化合并读取时才补充区域边界。高频读取用有界队列，显示刷新单独限频。

### 9.2 RTT

后台读取原始字节，记录通道与顺序。文本解码采用增量解码器，处理跨包字符和不完整行。清屏只改变显示历史，不默认删除已保存记录。

RTT消费者状态与目标是否输出分别记录；RTT空闲不自动判为断线。

### 9.3 串口

显示模型与会话分离：Core保留有界的方向片段及不可变快照，WPF的SerialLogView用原生只读富文本增量渲染，收发以颜色区分，不写入正文标记。默认跟随最新，用户上滚或选择文字后暂停跟随，使用“回到最新”恢复。冻结当前并分栏时右侧持有固定快照，左侧继续使用唯一串口会话的数据；继续显示仅关闭历史侧，不清实时历史，也不重放快照。清屏只清实时显示，重开串口只重置流解码与会话计数；完整历史仍以独立原始记录为准。首版不增加磁盘回放、搜索、筛选或时间旁栏。

首版COM使用字节流接口；NRF按电脑端普通COM处理。TCP串口及远端参数控制暂不实现，后续有明确场景再扩展。

收发、文件保存、显示独立调度。高速场景不逐字节刷新UI、不无限追加文本、不通过软件sleep实现微秒级RS485方向控制。

### 9.4 统一事件

数据事件包含来源、会话代次、序号、内容和质量状态；变量观测时间用于绘图。串口持久化以序号保证上位机观察顺序，时间戳可选；设备时间戳若已有则单独解释，不要求固件新增。事件缺口与批次数据顺序可检查，不将主机排序解释为跨方向的物理因果关系。

P1记录/回放通过同样的事件接口接入界面，回放模式禁用实际硬件写入。

## 10. Release 与版本管理

### 10.1 发布对象

首批产品产物为Windows x64便携ZIP、release-manifest.json、SHA256SUMS及包内说明/许可，内测范围与发布门引用需求4.1、AC-13。GUI、工作进程和稳定CLI同版交付；已验证Debug_LAN发布工具随包安装或离线导入，仍采用其独立版本。模板包及安装器后续增加，不作为首批前提。

工具API版本、工具实现版本、配置schema版本和模板来源版本分别记录。初期可以同一仓库标签发布多个产物，但不把这些版本含义合并。

### 10.2 安装与调用

工具发布 → 下载/离线导入到暂存目录 → 检查平台、清单、校验和接口兼容 → 安装到新版本目录 → 标记就绪 → 工程选择/锁定版本。

稳定CLI读取工程版本选择，从本机缓存定位工具。外部调用由便携启动器--cli进入当前内部组件；软件目录、组件目录和数据目录由RuntimePaths统一解析，旧接入迁移规则见详细设计6.2。稳定CLI属小助手安装组件；每个工具版本目录保留完整运行文件。所有被使用的版本不得原地覆盖。

当指定版本缺失时，CLI报告缺失以及安装入口，不能在正在执行烧录时自动选择其他版本。联网更新由GUI或独立工具管理命令完成。

### 10.3 升级性质

兼容实现修复可升级工具，不要求改GUI源码。新增必需参数、修改输出协议、改变配置含义或模板布局，需要版本协商/迁移。上游提交本身不改变已安装工具，只有完成发布、获取和选版才影响下游。

| 上游变化 | 维护与用户结果 |
| --- | --- |
| Debug_LAN内部兼容修复 | 上游发布工具包，用户导入/选版，无需重发客户端或手改脚本 |
| 工具调用/配置协议变化 | 维护者验证版本兼容，必要时修改客户端、迁移配置并发布新客户端 |
| 模板目录或字段结构变化 | 更新本仓适配规则与样本；当前适配规则编译进客户端，需随客户端发布，尚无独立在线适配包 |
| 服务端变化 | 保持已支持的Remote Server/网页手动接口；改变接口时评估兼容，不要求客户端每次跟随服务部署 |

一键准备工具是安装已发布组件，不是复制上游源码后另行维护。将Debug_LAN收进其他目录属于后续明确迁移，需要同步配置引用、兼容入口和来源记录，不能用目录整合代替依赖版本管理。

### 10.4 产品版本纪律

根 VERSION 是唯一产品版本来源，Directory.Build.props 统一注入 GUI、CLI、Worker 和包。修复/UI 打磨升 PATCH；兼容新能力升 MINOR 并清零 PATCH；不兼容配置、协议、接口或数据格式升 MAJOR 并清零后两位（0.x 同样执行）。保留预发布通道并将序号重置为 1。混合变更取最高等级；不因升版自动发布。

agent 根据真实影响填写 fix:/feat:/type!: 或 BREAKING CHANGE:，pre-commit 调用 scripts/version_guard.py 自动升级并暂存 VERSION，commit-msg 按提交信息只读校验。手动调整可用 scripts/bump_version.py --level patch|minor|major 或 --to；不能低于变更要求。未暂存版本冲突、升级失败和版本缺失均阻断。纯文档/测试/证据不升产品版本。打包及 CI 只读检查启用基线 121e075 之后的全部提交，防止用后续文档提交掩盖漏升；不追溯修改旧历史。

旧机制只检查格式及统一来源，没有比较产品源码提交前后版本，因此多次构建沿用 alpha.1；新机制参考 TeamHub 自动升版，但失败必须阻断，不采用 warn-only。Git 本地钩子可被人为绕过，CI 和打包承担第二层校验。外部 Debug_LAN 与协议 schema 仍独立版本。

默认交付及测试流程见 [.agents workflow](../.agents/workflows/change-test-deliver.md)，测试结束关闭本次创建的窗口。

### 10.5 Harness与发布分工

仓库门继续用标准库Python检查文档、账本、文件边界、样本和真实提交钩子。global.json锁定.NET SDK，C#项目提交packages.lock.json并用locked-mode恢复；静态检查、构建、测试由统一入口的显式--client编排。仓库门默认不构建，提交门仍使用暂存快照。无C#工程或SDK时预检返回未验证，不伪造产品通过。

verify.yml在push/PR/手动触发时运行仓库门；C#工程存在后运行客户端门并保存测试结果。release.yml仅workflow_dispatch，核对成功候选运行、完整SHA、产品版本及同一包的对应发布档证据（developer-preview允许明确延期实机验收），再上传原包到Pre-release；普通push不发布。发布job才授予contents:write，Actions固定完整SHA，不执行下载包中的exe。详见详细12.4。

App/Core/Worker/Cli、Windows自包含打包、候选上传和真实GUI成品自检已实施。H-03按用户授权AC-14完成首个开发Pre-release；云端验证38137241228与发布38137728563成功，原ZIP摘要一致。纯净Windows和硬件验收仍由C-05跟踪。仓库管理员权限已核实；分支保护未配置，工作流成功不代表强制合并保护。

## 11. 候选新建工程

P2入口复用Release管理和模板适配。用户选择系列、版本、名称与空目录后：

获取已确认的模板包 → 解压至暂存目录 → 按适配规则改名 → 在受控文件列表内完成工程名同步 → 校验结构和路径 → 移入目标目录 → 打开工程。

现有cleanup脚本具有删除/清理功能，不能仅因来自模板就在任意工作目录自动执行。新建阶段若复用，应限定到暂存工程并核对具体行为；不手工维护自动聚合cubemx.h。

已有工程模板升级不复用上述“覆盖式创建”流程，需单独设计差异迁移，当前不实施。

## 12. 可靠性与诊断

- 配置变更用快照、写入日志和恢复流程组织；多文件写入不视为文件系统天然原子操作。
- 进程与设备状态分开。进程活着、SDK已连、目标可读、数据更新均有独立证据。
- 重连设置有限退避和取消；不自动选择另一探针，不掩盖固件/ELF失配。
- 工具原始输出保留，错误映射到可理解原因；已知“退出码0但通信超时”不能报告成功。
- 独立串口原始保存可继续，界面过载可降刷新并标记显示裁剪；原始流丢弃需单独记录。
- ELF时间变化只提醒，不自动停采集或替换地址；用户更新地址时切换读计划。重新连接后重新定位RTT。
