# 修改、构建、桌面交付和测试

每次代码修改默认执行本流程，用户无需重复说明“打包测试”。

1. 读取实现、todo.json、test.json 和 Git 状态，保留其他未完成改动，明确本次验收点。
2. 修改代码及必要文档。涉及用户操作时，按下方“用户操作流程审查”确定本批路径并核对真实行为。agent 根据真实影响选择提交类型：修复/UI 打磨 `fix:`；兼容新功能 `feat:`；不兼容变更 `type!:` 或正文 `BREAKING CHANGE:`。
3. 执行相关验证并本地提交。pre-commit 自动升级并暂存唯一 VERSION，commit-msg 按提交信息只读校验；升级失败、版本过低或 VERSION 存在未暂存修改时阻断。不得用 `--no-verify` 绕过。
4. 从干净已提交源码执行 `python scripts/package_client.py --output dist/candidates/<版本>-<提交>-<用途>`，完成软件验证和成品自检。其他未完成工作不混入交付包；暂存的改动必须恢复。
5. 用 Windows Known Folder 获取桌面，完整候选目录移动到 `EmbeddedHelper_test/EmbeddedHelper-<版本>-<提交>-<用途>`。保留旧包和 data；校验清单、EXE/ZIP SHA256 及 ZIP 内 EXE。
6. 未指定范围时，只测本机软件及 UI。使用 Computer Use 检查桌面新包的相关页面、状态、布局、交互和错误提示，执行本批用户路径并保存证据；启动自检不代替界面检查。默认不连接探针、串口或远程硬件，不烧录或复位。用户指定硬件测试时按授权追加；缺少环境记未验证，继续完成独立检查。
7. 测试前记录已有窗口，记录本次创建的窗口和进程。无论成功失败，结束时停止本次采集并释放连接，关闭本次自己打开的应用、弹窗、浏览器标签、文件夹和辅助窗口；不关闭用户原有窗口、不按进程名批量终止。未保存内容或无法关闭须报告。
8. 完成的开发从 todo 移除，剩余验收及阻塞写入 test；结果绑定实际所验包，不把新提交或新构建自动算作已验收。设计记录源码版本、提交、桌面路径、实际测试结果和窗口清理证据，并本地提交。最后给出可点击路径。未经授权不 push、tag 或 release。

只有用户明确要求“只改代码并 commit、不编译”等才跳过构建、交付和 UI 启动；仍执行静态检查及产品版本升级。构建失败、工具不可用属于阻塞，不能记录为测试通过。

## 用户操作流程审查

涉及页面、配置或操作反馈的每批修改，使用个人技能 `$user-task-review`：修改前核对入口与实际事件/保存路径，桌面交付后验证本批首次使用、成功、失败及适用的保存/重启路径。单处文案或样式修改只覆盖受影响步骤，不自动扩大为全应用审计。

skill 保存可复用审查方法；本 workflow 负责执行时机、打包和证据归属，不在仓库复制个人技能。若该技能未安装，采用最低检查：用户能否知道用途、当前结果和下一步；反馈是否就地且不只靠颜色；说明是否重复；保存成功是否经过写入及回读确认。记录技能缺失，不跳过必要验收。

确认需要修改的问题写入 todo，单纯待测试、缺环境或用户暂缓写入 test；证据写入详细设计和 test-results。源码、模拟、真实 UI、设备验收分别说明；完成审查规则不代表页面已修复。窗口清理统一执行第 7 步。

## 自动版本选择

- MAJOR.MINOR.PATCH：修复、UI/文案打磨、兼容内部重构升 PATCH；兼容新能力升 MINOR 并清零 PATCH；不兼容配置、协议、接口或数据格式升 MAJOR 并清零后两位。0.x 同样执行。
- 混合变更取最高等级。脚本根据提交信息判定，agent 必须按真实业务影响填写；脚本不假装能理解代码语义。
- 保留 alpha/beta 通道，三段版本递增后预发布序号重置为 1，如 `0.3.0-alpha.1 -> 0.3.1-alpha.1`。不自动去掉预发布标记或发布。
- 每个产品源码提交均升级，包括明确不编译的提交。仅文档、证据、测试和工作流不升产品版本；同一提交重试构建不升级。手动指定版本不得低于自动最低版本。
- 本地钩子自动升级，打包只读检查，CI 对新增提交再次检查；任何失败必须阻断。已存在的历史提交不追溯改写。

提交前 agent 自动选择 VERSION_BUMP_LEVEL=patch/minor/major（默认 patch），或先运行 bump_version.py --level；新功能和不兼容变更必须选择对应等级。commit-msg 不修改版本，只阻断等级不足的提交。

pre-commit 不能读取尚未交给 commit-msg 的最终消息，因此不会自动从 feat/feat! 推断等级。若默认 patch 已暂存而 commit-msg 拒绝，先检查 `git diff --cached -- VERSION`；将 VERSION 调整到错误提示的最低版本或更高并 `git add VERSION` 后重试。失败不回滚已暂存版本；此时只改环境变量不会覆盖它。预先升版同样需要暂存，不能绕过未暂存 VERSION 冲突检查。
